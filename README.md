# 投研大盘数据采集系统

采集投研分析所需的大盘数据，提供 **Web 可视化看板**（一键采集、失败重跑、接口监控、定时调度、分类导出），同时保留命令行入口。**SQLite 为唯一实时主存储**，CSV / Excel 为按需导出快照。**ETF 与指数口径均为每个交易日（日频）**，宏观数据为月度与季度混合。

## 一、采集范围与数据源

| 类别 | 具体指标 | 数据源 | 频率 |
| --- | --- | --- | --- |
| 货币与信贷 | M0、M1、M2、居民储蓄存款、人民币存款余额、人民币贷款余额 | 中国人民银行（akshare 封装） | 月度 |
| 货币与信贷 | 社会融资规模存量 | 央行金融统计数据报告（权威锚点）+ 社融增量插值 | 月度 |
| 外贸 | 出口额、进口额、进出口总额 | 海关总署（akshare 封装） | 月度 |
| 消费与物价 | 社会消费品零售总额（当月）、CPI、PPI | 国家统计局（akshare 封装） | 月度 |
| 景气与市场 | 制造业 PMI、非制造业 PMI | 国家统计局（akshare 封装） | 月度 |
| 景气与市场 | A 股总市值（沪深）、央行黄金储备 | 交易所 / 国家外汇管理局（akshare 封装） | 月度 |
| 中国增长 | 中国 GDP（季度绝对值、同比增长） | 国家统计局（akshare 封装） | 季度 |
| 美国增长与物价 | 美国 GDP、CPI、核心 CPI、PPI、非农新增就业 | FRED（BEA / BLS / 美联储） | 月度 / 季度 |
| 美国利率 | 联邦基金目标利率上限、下限（实际值） | FRED（美联储） | 月度（日频取最新） |
| ETF | 每日份额（亿份）、单位净值（元）、规模（亿元） | 上交所 / 深交所官方份额 + 天天基金日净值 | **每个交易日** |
| 指数 | 上证指数、沪深300、科创50、创业板指：开高低收、成交量、涨跌幅 | 新浪财经日线（akshare 封装） | **每个交易日（近一年）** |

共 **25 个宏观指标（17 项原指标 + 中国 GDP + 7 项美国指标，月度/季度混合）+ ETF 日频数据 + 4 个指数近一年日线数据**。每条记录带 `单位` 字段，不同指标单位不同。

> **重要说明**：央行官网统计数据**不包含 ETF 数据**，因此 ETF 数据来自交易所官方披露的每日份额，配合天天基金每日单位净值计算规模。

**口径说明**：
- **ETF 规模** = 份额(亿份) × 单位净值(元/份)，为计算值，与基金公司定期报告净资产可能有细微差异。
- **指数**：默认采集近一年（365 天）交易日日线，标的与区间可在 Web「指数标的配置」中灵活调整；涨跌幅由相邻交易日收盘价环比计算，每只指数区间首日为空。
- **进出口**原始数据为千美元，已换算为**亿美元**。
- **社融存量**：akshare 无存量接口，采用「权威锚点 + 社融增量插值」——央行每月报告公布的月末存量为锚点（代码中 `SFR_ANCHORS` 可增补），锚点之间月份按增量分配。锚点月为央行权威值，其余为插值估算。
- **中国 GDP**：取统计局季度累计绝对值，日期映射为季末月（Q1→03、Q2→06、Q3→09、Q4→12），同比取自接口「国内生产总值-同比增长」。
- **美国 CPI / 核心 CPI / PPI**：FRED 指数水平；同比按上年同月、环比按上月计算（缺失月份自动跳过）。美国非农新增就业由 FRED 总就业人数月度差分得到，单位千人。
- **美国利率上下限**：取 FRED 联邦基金目标利率上限 `DFEDTARU` 与下限 `DFEDTARL` 的**实际值**；原始序列为日频，按月取月末最新有效值，单位 %。

## 三、安装与运行

```bash
pip3 install -r requirements.txt

# 首次从旧版 CSV/JSONL 迁移到 SQLite（幂等，可重复执行）
python3 migrate_to_sqlite.py

# 采集全部数据（宏观 + ETF 日频 + 指数近一年日线），写入 SQLite
python3 main.py

# 全量采集并统一指定日期范围（覆盖各类别配置默认值；留空则沿用配置）
python3 main.py --start 2024-01-01 --end 2024-06-30

# 只采集 ETF 日频 / 只采集宏观 / 只采集指数
python3 main.py --etf-only
python3 main.py --macro-only
python3 main.py --index-only

# 精确采集（按类别 + 代码 + 时间范围）
python3 main.py --collect-interface --category index --codes 000001,399006 --start 2026-01-01 --end 2026-11-20

# 指定配置文件、覆盖导出格式
python3 main.py --config config.json --output-format excel

# 接口运维监控
python3 main.py --monitor-report    # 从 SQLite 生成历史监控报告（不采集）
python3 main.py --retry-failed      # 重跑最近一个「有失败」批次的失败接口（含指数接口）

# 导出数据：Web 看板点击「导出宏观 / 导出 ETF / 导出指数 / 导出监控 / 导出全量」
# 对应 API：POST /api/export/macro|etf|index|monitor|full
```

## 四、配置说明

编辑 `config.json`：

```json
{
  "etf": {
    "codes": ["510300", "510050", "510500", "159915", "588000"],
    "start_date": "",
    "end_date": "",
    "default_trade_days": 20
  },
  "macro": { "start_date": "2024-01" },
  "storage": {
    "backend": "sqlite",
    "db_path": "output/market_data.db",
    "auto_export_on_collect": false
  },
  "output": { "formats": ["csv", "excel"], "keep_snapshots": 3 },
  "fetch": { "retry": 3, "retry_interval_sec": 2, "timeout_sec": 15 },
  "monitor": { "history_file": "output/monitor/interface_runs.jsonl" }
}
```

- **storage.backend**：`sqlite` 为实时主存储；`file` 仅用于旧版回滚。
- **storage.auto_export_on_collect**：默认 `false`，采集只写 SQLite；文件导出按需触发。
- **etf.codes**：要采集的 ETF 代码（6 位数字）。**注意：ETF 配置与上市日期已迁入 SQLite，config.json 仅作镜像**；以后以 Web「ETF 标的配置」或 `/api/etf/config` 为准。填 `[]` 则跳过 ETF 采集。
- **etf.start_date / end_date**：日频数据区间，格式 `YYYY-MM-DD`。两者留空时，`end_date` 取今天，`start_date` 取往前 `default_trade_days` 个交易日。
- **etf.default_trade_days**：留空日期时默认采集最近 N 个交易日，默认 20。N 越大，上交所逐交易日查询耗时越长。
- **index.codes**：要采集的指数代码，支持 `000001`（上证指数）、`000300`（沪深300）、`000688`（科创50）、`399006`（创业板指）。**指数配置已迁入 SQLite，config.json 仅作镜像**；以后以 Web「指数标的配置」或 `/api/index/config` 为准。
- **index.lookback_days**：采集范围，近 N 天（默认 365 = 近一年）；也可用 `start_date / end_date` 覆盖。
- **macro.start_date**：宏观数据起始月份 `YYYY-MM`，留空取全部历史。
- **fetch**：网络重试次数、间隔与超时。单只 ETF / 单个交易日 / 单个指数失败不会影响其余数据。
- **monitor.history_file**：旧版接口调用历史（JSONL），迁移后保留只读基线；实时监控已写入 SQLite 的 `interface_run` 表。

### SQLite 主存储与业务主键

| 表 | 业务主键 | 示例 |
| --- | --- | --- |
| `macro_observation` | `{指标代码}_{YYYYMM}` | `M2_202610` |
| `etf_observation` | `{6位基金代码}_{YYYYMMDD}` | `510050_20261020` |
| `index_observation` | `{6位指数代码}_{YYYYMMDD}` | `000001_20261120` |
| `interface_run` | `{run_id}_{接口键}_{运行时间}_{序号}` | `20261122_201814_interface_macro.fred_DFEDTARU_20261122_201814_001` |
| `collection_stat` | `{run_id}\|{类别}\|{细分代码}` | `20261122_201814_full\|ETF\|510050` |
| `etf_config` | `main` | 代码清单、上市日期、日期区间、默认交易日数 |
| `index_config` | `main` | 指数代码清单、日期区间、回看天数 |
| `meta` / `export_log` | key / id | 迁移标记与导出记录 |

所有业务写入均使用 `ON CONFLICT(biz_key) DO UPDATE`，因此全量采集、精确采集、失败重跑都不会产生重复行。

## 五、接口运维监控与失败重跑

每次运行会为**每个采集接口**记录一条状态，写入 SQLite 的 `interface_run` 表；Web 看板直接查询该表。**不再自动生成** `运维监控报告_*.xlsx`，可在「接口监控看板」点击「导出监控」按需生成（含口径说明）。

**监控什么（逐接口）**

| 接口 | 覆盖 |
| --- | --- |
| 宏观 11 个 akshare 接口 | M0/M1/M2、存贷款、社融增量、进出口、社零、CPI、PPI、PMI、A股市值、黄金储备 |
| ETF 交易日历 | 交易日列表获取 |
| ETF 上交所份额 | 每个交易日一次调用（N 个交易日 = N 条记录） |
| ETF 深交所份额 | 日期区间一次调用 |
| ETF 天天基金净值 | 每只基金一次调用（N 只 = N 条记录） |

每条记录包含：**运行日期**、运行类型（full/retry）、接口键与名称、调用参数、状态（success/failed）、尝试次数、数据行数、**失败原因**、耗时。完整回答「哪天、哪个接口失败、为什么失败」。

**监控报告五个 sheet**

- `运行总览`：每批次调用数、成功/失败数、成功率、总耗时
- `失败明细`：逐条失败记录（失败日期、接口、原因、尝试次数）+ **重跑结果**标注
- `接口健康度`：每个接口累计调用/失败次数、成功率、最近失败日期与原因
- `调用明细`：全部调用记录，便于审计
- `采集量统计`：每次采集按**类别口径（宏观/ETF/指数）+ 细分口径（指标/基金/指数代码）**的入库行数，写入 SQLite `collection_stat` 表，同批次同代码覆盖更新

**调用参数与失败原因**：每条记录的参数不再只有时间——宏观含 `interface`（akshare 函数名 / FRED 序列）、`source`（数据源）、FRED 的 `series_id` 与 `url`；ETF 含 `market`、`url`、`sqlId`/`catalog_id`/`jjlb` 等交易所请求参数；指数含 `symbol`、`interface`、`source`、`lookback_days`。失败原因为结构化文本：`异常类型: 消息 | HTTP 状态 | URL | 响应片段 | 补充上下文`（HTTP 接口自动提取响应状态码与片段）。

**失败重跑机制**

```bash
python3 main.py --retry-failed     # 重跑最近一个「有失败」批次的失败接口
python3 main.py --monitor-report   # 单独生成监控报告
```

工作流程：

1. 从历史记录定位最近一个含失败的批次，列出每个失败接口的原因。
2. 宏观失败接口 → 只重采这些接口（按函数名精确重跑）。
3. ETF 份额失败 → 只重采失败的交易日/区间；ETF 净值失败 → 只补采失败基金的净值，份额沿用主数据，避免无谓重采引入新故障。
4. 重跑结果以非空字段覆盖合并到最新数据，并**统一重算规模**（份额 × 净值）；合并后写入新 CSV/Excel。
5. 重跑批次以新 run_id 记入历史，失败明细中标注「已重跑成功（日期/批次）」或「未重跑成功」。
6. 关键设计：即使之后又成功跑过一次，仍能重跑上一批次的失败接口（按最近含失败批次定位，而非最近批次）。

> 重跑只针对**临时性故障**（网络抖动、接口超时、502 等）。若接口变更导致字段缺失、或 ETF 代码本身无效，需修复代码或配置，重跑不会解决。

## 六、输出字段

**ETF 规模（日频）**：`基金代码`、`基金简称`、`交易市场`、`交易日期`、`份额(亿份)`、`单位净值(元)`、`规模(亿元)`、`数据源`、`采集时间`

- 交易市场：`SH` 上交所 / `SZ` 深交所
- 每个 ETF × 每个交易日一行，便于直接做时间序列分析和面板回归

**指数日线（近一年交易日）**：`指数代码`、`指数名称`、`交易日期`、`开盘价`、`最高价`、`最低价`、`收盘价`、`成交量`、`涨跌幅(%)`、`数据源`、`采集时间`

- 默认近一年（365 天），每个指数 × 每个交易日一行；涨跌幅为环比计算值，区间首日为空。

**宏观数据（月度/季度/会议混合）**：`指标代码`、`指标名称`、`日期`、`数值`、`单位`、`同比(%)`、`环比(%)`、`数据源`、`采集时间`

## 八、注意事项与扩展

1. **日频口径**：ETF 数据按交易日采集，非季末快照。若某标的在某交易日无数据（停牌、新上市等），该日不会出现该标的行。
2. **规模为计算值**：用份额 × 单位净值计算，适合做日频变化趋势分析；如需与基金公司披露的精确净资产对齐，请以定期报告为准。
3. **历史回补**：设置 `start_date` / `end_date` 即可回补任意区间；上交所按日查询，深交所一次请求返回整段区间，区间越长上交所耗时越久。
4. **社融存量**：锚点月为央行公布权威值，其余月份按社融增量插值。要更新权威锚点，在 `collectors/macro.py` 的 `SFR_ANCHORS` 字典中增补央行每月报告公布的月末存量即可。
5. **社零 2 月**：国家统计局对 1-2 月社零合并统计、不单独公布 2 月当月值，故该月无记录（属数据源正常缺失，已过滤空值行）。
6. 命令行仍可用：`python main.py` 全量采集，`--retry-failed` 重跑，`--monitor-report` 出监控报告。

### 关键机制

- **异步任务**：采集/重跑在后台线程执行，同一时刻只允许一个任务（避免并发写同一批文件），前端轮询 `/api/jobs/{id}` 实时显示日志与状态。日志只在 root 挂一次 handler，不重复。
- **实时日志**：默认在采集控制台右侧以单行滚动条显示最新日志；点击可展开完整日志，轮询只追加新增行，保持自动滚动，可暂停或一键回到底部。
- **单项采集保护**：SQLite 按业务主键 upsert；精确采集仅采单一类别/指标时，其它类别数据保持库中原样，不会被空 DataFrame 覆盖。
- **全量采集日期范围**：控制台全量采集可指定起止日期（默认 2024-01-01 至当天，支持一键重置），后端用该范围统一覆盖宏观、ETF、指数三类的配置日期；`POST /api/collect` 的 `start` / `end` 为可选字段，留空则沿用 `config.json` 各类别默认值。命令行对应 `python main.py --start ... --end ...`。
- **日期区间兼容**：所有日期控件默认 2024-01-01 至当天；前端统一传 YYYY-MM-DD，宏观采集与查询自动按月截取为 YYYY-MM。
- **定时调度**：服务运行时按 `config.json` 的 `scheduler` 段每日指定时刻自动采集一次（同一天只触发一次），可在看板实时开关/改时间。任务与失败会在看板突出显示。
- **SQLite 主存储**：业务数据、接口监控、ETF 配置与上市日期、指数配置均在 `output/market_data.db`；旧 CSV/JSONL 保留只读作为迁移与回滚基线。
- **分类导出**：采集只写库不生成文件；按需导出宏观 / ETF / 指数 / 接口监控，每个 Excel 都含「口径说明」Sheet，CSV 同步生成独立口径说明文件；全量导出打包 ZIP（含宏观/ETF/监控三类，指数可单独导出）。
- **口径化清理**：`POST /api/clean/preview` 只读预览将删除的行数（含样本）；`POST /api/clean` 必须携带 `confirm=true` 才执行，按类别 / 细分代码 / 时间范围精确删除 `*_observation` 表行（宏观按 YYYY-MM、ETF/指数按 YYYY-MM-DD 比较，代码自动补零至 6 位）。删除不可撤销，但**不触发采集、不影响配置 / 监控 / 导出记录**，服务启动/重启也不会调用。
- **监控清理**：`POST /api/monitor/clean/preview` 预览、`POST /api/monitor/clean`（需 `confirm=true`）执行，仅删 `interface_run` 表；支持时间 / 状态 / 运行类型 / 类别 / 关键词组合，不影响业务数据与配置。入口在接口监控看板「导出监控」按钮之后，需二次确认。
- **输出文件视图**：`/api/files` 过滤掉 `exports/` 目录，仅展示采集生成的原始文件；导出产物仍可通过导出按钮自动下载与 `/api/download` 获取。
